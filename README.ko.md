> 회의록, 이메일, 엑셀 수식, 데이터 정리, 간단한 웹페이지까지 — 반복되는 문서 업무를 **GitHub Copilot**에게 맡기고, 판단은 내가 하는 법을 배웁니다. 코딩 경험은 필요 없습니다.
>
> 🇺🇸 **English guide** → [README.md](README.md)

**형식:** 하나의 스토리 · 짧은 랩 8개 · 핵심 실습 약 3시간 · **도구:** GitHub Copilot 앱 (Mac/Windows/Linux) · **대상:** 기획, 마케팅, 영업·CS, 인사, 재무, 디자인, 운영 — 텍스트와 표로 일하는 모든 사람.

- 직접 다룰 줄 아는 **GitHub Copilot 앱** 작업 환경

1. **① 개념편** — Copilot이 사무 업무에서 실제로 무엇인지, 그리고 모든 것의 기반이 되는 두 가지 습관(잘 요청하기, 잘 검증하기)을 15분 분량으로 읽습니다.

3. **③ 레퍼런스편** — 직군별 플레이북, 프롬프트 패턴, 보너스 랩, 트러블슈팅, 용어 사전, 워크숍 진행자 노트.

# ① Part 1 — 개념편

## 1. Copilot은 개발자 전용이 아니다

"코더용 자동완성"이라는 Copilot의 유명세는 진짜 강점을 가립니다: **구조화된 텍스트를 만들고 변형하는 능력**입니다. 그리고 사무 업무의 상당수는, 알고 보면 옷만 갈아입은 구조화된 텍스트입니다:

| 여러분이 이미 만드는 것 | 사실은 이것 | Copilot과 만나면 |
| --- | --- | --- |
| 회의록, 위키, 체크리스트 | **Markdown** (`.md`) | 문서 초안·재구성·요약을 몇 초 만에 |
| 스프레드시트와 각종 내보내기 파일 | **CSV** + **수식** | 수식 생성·해설, 데이터 정제와 질문 |
| 뉴스레터, 랜딩페이지, 초대장 | **HTML** | 말로 설명하면 진짜 열리는 페이지가 나옴 |
| 앱 설정, 폼 응답 내보내기 | **JSON / YAML** | "무서운 설정 파일"을 통역사와 함께 읽고 고침 |
| "그 숫자 좀 뽑아줄 수 있어요?" | **SQL** | 일상 질문을 분석가가 돌릴 쿼리로 변환 |

비개발자의 발목을 잡는 세 가지 통념도 지금 정리하고 갑시다:

| 통념 | 이 가이드가 보여줄 것 |
| --- | --- |
| *"먼저 코딩부터 배워야 할 텐데."* | 여러분은 **요청서**를 한국어로 쓰고, 기술 산출물은 Copilot이 씁니다. 여러분의 일은 구체적으로 지시하고 결과를 판단하는 것 — 이미 갖고 있는 능력입니다. |
| *"결국 창만 다른 챗봇 아닌가."* | 웹 챗봇과 달리 Copilot은 **내 파일 옆에** 삽니다. 실제 회의 메모를 읽고, 실제 CSV를 고치고, 실제 HTML 파일을 만들어 줍니다. 복사–붙여넣기 셔틀이 사라집니다. |
| *"AI 결과물은 실무에 못 믿는다."* | 맞습니다 — **검증 안 한** 결과물은요. 그래서 이 가이드는 모든 랩에 검증 습관을 심어 놓았습니다. 신뢰는 감정이 아니라 업무 절차입니다. |

## 2. 작업대 소개: GitHub Copilot 앱

왜 브라우저 챗봇이 아니라 데스크톱 앱일까요? **파일과 AI가 한곳에 있기** 때문입니다. GitHub Copilot 앱은 AI 에이전트를 *지휘*하기 위해 만들어진 앱입니다: 세션에서 업무를 설명하면, 에이전트가 프로젝트의 실제 파일을 읽고, 실제 파일을 써넣고, 행동하기 전에 여러분의 승인을 구합니다. Mac/Windows/Linux에서 무료로 쓸 수 있고, 개발자용으로 만들어졌음에도 필요한 건 딱 **여섯 가지**뿐입니다:

| # | 무엇 | 어디 | 용도 |
| --- | --- | --- | --- |
| 1 | **Sessions** (+) | 사이드바 | 세션 하나 = 내 프로젝트 안에서 일하는 에이전트와의 대화 하나 |
| 2 | **프롬프트 입력창** | 세션 하단 | 에이전트에게 브리핑하는 곳 |
| 3 | **모드·모델 선택** | 입력창 아래 드롭다운 | Interactive / Plan / Autopilot · 모델은 **Auto**면 충분 |
| 4 | **`@` 파일 참조** | 입력창에 입력 | 특정 파일을 에이전트에게 지목 (`@practice/ko/orders.csv`) |
| 5 | **Changes** | 입력창 위 | 에이전트가 무엇을 바꿨는지 확인 |
| 6 | **Chats** | 사이드바 | 파일과 무관한 빠른 질문 |

나머지 — My work, Automations, Canvases — 는 당분간 몰라도 됩니다.

### 세션의 세 가지 모드 (그리고 Chats)

| 모드 | 하는 일 | 이럴 때 |
| --- | --- | --- |
| **Interactive** | 에이전트와 주고받으며 진행. 제안하고, 내 입력을 기다림 | 이 가이드의 모든 랩 기본값 |
| **Plan** | 에이전트가 계획서를 먼저 쓰고, 내가 승인해야 실행 | 미리 보고 싶은 큰 작업 — Lab 7에서 시도 |
| **Autopilot** | 기다리지 않고 완료까지 자율 진행 | 브리핑이 빈틈없을 때만 |
| **Chats** (사이드바) | 프로젝트·파일을 건드리지 않는 일반 대화 | 파일 없는 질문 — Lab 3은 여기서도 가능 |

> 💡 **경험칙:** **Interactive**에 머물면서 타이핑은 에이전트에게 맡기세요. 파일을 만들거나 명령을 실행하기 전에 허락을 구하는 건 버그가 아니라 기능입니다 — 요청 내용을 읽고 승인하세요.

## 3. 요청하는 법: 4요소 요청

밋밋한 답과 정확한 답의 차이는 대개 모델이 아니라 **요청**에서 갈립니다. 믿을 만한 요청에는 네 가지 요소가 있습니다 — **회사 사정을 전혀 모르는, 대신 엄청나게 빠른 신입 동료에게 주는 업무 지시서**를 쓴다고 생각하세요:

| 요소 | 답하는 질문 | 예시 조각 |
| --- | --- | --- |
| **목표** | 무엇을 받고 싶은가? | "이 고객 메일에 대한 답장 초안을 써줘." |
| **맥락** | 무엇을 보고/알고 해야 하는가? | "첨부한 메시지 기준. 우리는 작은 문구 회사고, 지연은 택배사 실수였어." |
| **형식** | 어떤 모양이어야 하는가? | "150자 내외, 제목 포함, 따뜻하고 담백한 한국어." |
| **가드레일** | 꼭 지킬 것 / 하지 말 것은? | "사과는 한 번만, 택배사 탓 금지, 재발송 또는 환불 제시. 주문 정보를 지어내지 말 것." |

같은 업무, 전과 후:

> ❌ "이 고객한테 답장 좀 써줘"
>
> ✅ "첨부한 고객 메일의 답장 초안을 써줘. 맥락: 우리는 12명 규모 문구 회사이고, 다른 상품이 배송된 데다 도착도 늦었어. 형식: 제목 포함 150자 내외, 따뜻하지만 프로페셔널하게. 가드레일: 사과는 한 번만 하고 누구 탓도 하지 말 것, 정상 상품 재발송+보상 또는 배송비 포함 전액 환불 두 가지를 모두 제시할 것, 고객이 말하지 않은 사실은 쓰지 말 것."

매번 네 요소를 다 채울 필요는 없습니다. 다만 답이 실망스러울 때 어느 요소를 빼먹었는지 확인해 보세요 — 대개 그게 해결책입니다.

## 4. 검증하는 법: 최종 결재자는 나

Copilot은 자신감 넘치는 초안 작성자이지, 진실의 원천이 아닙니다. 숫자를 잘못 읽을 수 있고, 빈칸을 "그럴듯한 무언가"로 친절하게 채울 수 있고, 거의 맞는(그래서 더 위험한) 수식을 내놓을 수 있습니다. **검증이 업무 절차에 들어 있다면** 전혀 문제가 되지 않습니다:

1. **사실 대조.** 초안이 나오면 이름·날짜·숫자·약속을 원본과 하나하나 대조합니다. (랩마다 *"불확실하거나 없는 정보는 TBD로 표시하고 지어내지 마"*라는 지시가 들어 있습니다 — 이 문장은 평생 훔쳐 쓰세요.)
2. **하나는 재계산.** Copilot이 매출을 합산했다면 한 줄만 골라 직접 계산해 보세요. 정직한 표본 검사 하나가 구조적 오류 대부분을 잡습니다.
3. **자백 받기.** *"네가 가정한 것과 확신이 없었던 부분을 나열해줘."* 이 한 문장이 조용한 추측을 놀랄 만큼 많이 끌어냅니다.
4. **믿기 전에 테스트.** 수식과 페이지는 작은 테스트 케이스를 요청해서 직접 돌려본 뒤 채택합니다.
5. **붙여넣기 전에 생각.** 이 저장소의 실습 파일은 가상입니다. 실무에서는 회사의 AI 정책을 따르세요 — 실제 고객 정보, 계정 정보, 미공개 재무 데이터는 조직이 명시적으로 허용하지 않는 한 어떤 AI 도구에도 넣지 않습니다.

> 🔑 개념편에서 한 문장만 기억한다면: **코딩을 배우는 게 아니라, 브리핑과 리뷰를 배우는 것입니다.** 둘 다 좋은 관리자가 이미 하는 일입니다.

> 👉 랩은 **위에서 아래로** 진행하세요. 각 프롬프트 블록을 세션 입력창에 입력(또는 붙여넣기)하고, ✅ **체크포인트**를 통과한 뒤 다음으로 넘어갑니다. 여러분의 결과는 옆자리와 다를 겁니다 — 생성형 AI의 정상 동작이며, 체크포인트는 그걸 감안해 만들었습니다.

## Lab 0 — 작업대 세팅

> 🎯 설치, 로그인, 프로젝트 연결, 첫 대화 · ⏱️ 약 15분

**1. Git 설치** → [github.com/git-guides/install-git](https://github.com/git-guides/install-git). Copilot 앱이 내부적으로 쓰는 저장·버전 관리 엔진입니다 — 한 번 설치하고 나면 존재를 잊어도 됩니다.

**2. GitHub Copilot 앱 설치** → [github.com/features/ai/github-app](https://github.com/features/ai/github-app) — 내 플랫폼용을 내려받아 실행합니다.

**3. 로그인:** **Sign in to GitHub**를 눌러 안내를 따릅니다. 유료 플랜이 없어도 **Copilot Free**면 이 가이드를 완주할 수 있습니다. (온보딩에서 저장소 선택을 물으면 건너뛰어도 됩니다 — 다음 단계에서 직접 연결합니다.)

## Lab 3 — 겁나지 않는 엑셀 수식

## 보너스 랩

### 보너스 랩 B1 — SQL 맛보기

SQL은 "그 숫자 좀 뽑아주세요"의 언어입니다 — 그리고 여러분은 이제 그것을 *읽을* 준비가 됐습니다. 쓰던 세션에서:

```text
@practice/ko/orders.csv가 orders라는 데이터베이스 테이블이라고 가정하고 SQL을 써줘:
1. 상품별 매출, 높은 순으로
2. 2026년 8월의 채널별 주문 수
3. 두 번 이상 주문한 고객
각 쿼리를 한 줄씩 쉬운 말로 설명하고, 아까 본 데이터 품질 문제 중 어떤 것이
이 결과를 조용히 오염시키는지도 알려줘.
```

마지막 문장이 핵심입니다: 더러운 데이터는 에러를 내지 않습니다, 거짓말을 하죠. 오늘 데이터베이스가 필요한 건 아닙니다 — 쿼리를 읽고 그 입력을 의심할 수 있다는 것만으로 분석가와의 대화가 달라집니다.

### 보너스 랩 B2 — 메일함에서 살아남는 이메일

웹페이지와 HTML 이메일은 다른 생물입니다(이메일 클라이언트는 과거에 살고 있어서, 표 기반 레이아웃과 인라인 스타일이 이깁니다). 다음을 보내세요:

```text
my-work/newsletter.html을 만들어줘: 종이와 호박 팝업을 알리는 HTML 이메일.
이메일 클라이언트에서 안전하게(표 기반 레이아웃, 인라인 스타일, 외부 리소스
없음), 최대 600px 너비, 히어로 1개, 하이라이트 3개, 버튼 1개(RSVP),
{수신거부_링크} 플레이스홀더가 있는 텍스트 푸터. 다 만들고 나서, HTML
이메일이 웹페이지와 다른 점 5가지를 알려줘.
```

브라우저로 열어 미리 보세요. 발송은 메일 도구의 몫이지만, 제작에 더 이상 외주가 필요 없습니다.

### 보너스 랩 B3 — 정리는 에이전트에게

에이전트는 **프로젝트 전체**를 대상으로 움직일 수 있습니다 — 진짜 자동화의 시작점입니다. 해보세요:

```text
my-work/ 안의 모든 파일을 살펴보고 my-work/README.md를 만들어줘: 파일별로
무엇인지, 어느 랩에서 만들었는지, 한 줄 설명이 있는 표. 맨 위에는 자기
평가서에 붙여넣어도 될 "포트폴리오 요약" 문단 하나.
```

읽고, 계획하고, 쓰기 전에 승인을 구하는 과정을 지켜보세요. 그 검토–승인 루프가 바로, 시간을 아끼면서도 자동화를 안전하게 유지하는 방법입니다. 그다음 사이드바의 **Automations**를 살펴보세요: 같은 요청을 작업으로 저장하면 일정에 맞춰, 또는 원할 때마다 실행됩니다 — 정리가 스스로 정리하는 셈이죠.

### 보너스 랩 B4 — 터미널 맛보기 (Copilot CLI)

순전히 선택, 호기심 있는 분들을 위해: Copilot 앱의 심장은 [GitHub Copilot CLI](https://docs.github.com/copilot/concepts/agents/about-copilot-cli)입니다 — 창 하나 없이 **터미널에서** 직접 몰 수도 있죠. Node.js 22+가 설치되어 있다면:

```bash
npm install -g @github/copilot
cd ghcp-for-non-developers
copilot
```

폴더를 신뢰하겠냐고 물으면 수락하고, 마우스 없이 Lab 1을 해보세요:

```text
practice/ko/meeting-notes.txt를 Markdown 회의록으로 정리해서
my-work/minutes-cli.md로 저장해줘. 없는 정보는 TBD로 표시하고 지어내지 마.
```

계획하고, 승인을 구하고, 파일을 씁니다. 여기서 *바뀌지 않은 것*에 주목하세요: 4요소 요청과 검증 체크리스트는 앱이든 터미널이든 웹이든 모든 Copilot 환경에서 통합니다. 도구는 바뀌어도, 브리핑하고 리뷰하는 실력은 평생 여러분 것입니다.

## 검증 체크리스트

인쇄해 붙여둘 만한 목록. Copilot의 결과물이 내 손을 떠나기 전에:

- [ ] **사실:** 모든 이름·날짜·숫자·약속을 원본과 대조했다
- [ ] **재계산 하나:** 최소 한 개의 계산을 직접 검증했다
- [ ] **자백:** 가정/불확실한 부분을 물어보고 읽었다
- [ ] **빈칸은 TBD:** 모르는 것은 그럴듯한 창작이 아니라 TBD로 표시되어 있다
- [ ] **테스트 실행:** 수식/페이지는 채택 전에 한 번 돌려봤다
- [ ] **데이터 위생:** 회사 AI 정책이 허용하지 않을 것은 아무것도 붙여넣지 않았다

## FAQ

**내 결과가 가이드 설명과 달라요. 고장인가요?**
아닙니다 — 생성형 AI는 실행할 때마다 결과가 다릅니다. 그래서 모든 랩이 정확한 문장이 아니라 *속성*("한눈 요약이 있는가", "수량이 미결 질문으로 처리됐는가")을 확인합니다.

**내 데이터가 모델 학습에 쓰이나요?**
플랜과 조직 설정에 따라 다릅니다 — 관리자에게 묻고, 회사 AI 정책을 읽고, 그전까지는 실제 고객·재무 데이터를 넣지 마세요. 이 저장소의 실습 파일이 전부 가상인 이유가 바로 마음 놓고 연습하기 위해서입니다.

**왜 챗봇 웹사이트가 아니라 데스크톱 앱인가요?**
파일, 그리고 손 때문입니다. 웹 챗봇은 말만 할 수 있지만, Copilot 앱의 에이전트는 실제 CSV를 읽고 그 옆에 실제 HTML 파일을 만들어 줍니다 — 복사–붙여넣기 세금이 사라지죠. 일에 *대해* 수다 떠는 게 아니라, 일을 *지시*하는 겁니다.

**문법을 외워야 하나요?**
아니요. 필요한 건 4요소 요청과 검증 체크리스트뿐입니다. 문법은 Copilot의 일이고, 판단이 여러분의 일입니다.

**Copilot이 자신만만하게 틀렸어요. 덜 믿어야 하나요?**
빠르고 지치지 않지만 가끔 과신하는 신입 동료만큼만 믿으세요: 초안은 훌륭하게, 검토는 전부. "자신만만하게 틀리기"는 AI와 인간 모두의 알려진 실패 모드라서 체크리스트가 존재하는 겁니다.

## 용어 사전 (쉬운 말로만)

| 용어 | 여기서의 의미 |
| --- | --- |
| **저장소(리포)** | GitHub에 사는 프로젝트 폴더. 이 가이드도 하나입니다. |
| **클론 / ZIP 다운로드** | 저장소를 내 컴퓨터로 복사하는 두 가지 방법(git 방식 / 일반 방식). |
| **Git** | 앱이 작업을 안전하게 지키려고 쓰는 버전 관리 엔진. 한 번 설치하면 보이지 않습니다. |
| **GitHub Copilot 앱** | 내 프로젝트 파일을 다루는 AI 에이전트를 지휘하는 데스크톱 앱. 우리의 작업대. |
| **세션(Session)** | 프로젝트 하나 안에서 에이전트 하나와 나누는 대화 하나. 앱 사이드바에 삽니다. |
| **Markdown (.md)** | `#`, `-`, `\|` 같은 가벼운 기호가 제목·목록·표로 변하는 일반 텍스트. |
| **Changes** | 에이전트가 정확히 무엇을 바꿨는지 보여주는 앱 화면. |
| **CSV** | 쉼표로 구분된 일반 텍스트 형태의 표 데이터. 엑셀로 열립니다. |
| **HTML** | 웹페이지의 파일 형식. 브라우저로 열립니다. |
| **SQL** | 데이터베이스에 질문하는 언어. |
| **프롬프트** | 여러분이 입력하는 요청. 브리핑이 좋을수록 결과물이 좋습니다. |
| **Interactive / Plan / Autopilot** | 세션 모드: 주고받기 / 계획 먼저, 승인 후 실행 / 완료까지 자율 진행. |
| **모델 선택기** | 세션을 구동할 AI 모델을 고르는 드롭다운. **Auto**면 충분합니다. |

## 진행자 노트

워크숍으로 진행하시나요? 검증된 구성들:

| 형식 | 시간 | 범위 |
| --- | --- | --- |
| **맛보기** | 90분 | Lab 0~2 + 검증 체크리스트 5분 |
| **반일** | 약 3.5시간 | Lab 0~5, Lab 3 후 10분 휴식 |
| **종일** | 약 6시간 | 전체 + 캡스톤 3분 발표 |
| **점심 시리즈** | 45분 × 4회 | (0+1) / (2+3) / (4+5) / (6+7) |

**행사 전 (성패를 가르는 목록):**

- [ ] 모든 참가자가 도착 전에 GitHub 계정과 **Copilot 사용 권한을 확인**했다 — 현장 장애의 90%가 여기서 납니다
- [ ] Copilot 앱 **및 Git** 설치 완료, 또는 Lab 0에 20분 추가 배정
- [ ] 행사장 와이파이에서 github.com과 Copilot 엔드포인트가 열린다
- [ ] 진행자 본인이 **이번 주에** 전체 랩을 직접 돌려봤고(UI는 계속 바뀝니다), 시연 보험용으로 결과 스크린샷을 준비했다

**진행 중:**

- 초반에 규칙 선언: *"여러분의 결과는 옆 사람과도, 저와도 다릅니다. 우리는 단어가 아니라 속성을 확인합니다."*
- 짝 구성: **드라이버**가 입력하고 **내비게이터**가 체크포인트를 소리 내어 읽습니다. 랩마다 교대.
- 누군가 이상한 답을 받으면 프로젝터에서 *요청*을 함께 디버깅하세요 — 4요소 중 무엇이 빠졌나? 최고의 교육 순간이 거기 있습니다.
- 캡스톤 발표: 3분, "무엇을 만들었나 / 잘 통한 프롬프트 하나 / 고쳐야 했던 것 하나". 성공담보다 수정담이 더 많이 가르칩니다.
